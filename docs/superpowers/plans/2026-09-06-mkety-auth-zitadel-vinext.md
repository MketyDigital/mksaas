# Mkety Auth + ZITADEL Adapter + vinext Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace Auth.js/NextAuth with a provider-neutral Mkety Auth core, implement ZITADEL as the first OIDC adapter, preserve existing Mkety tenant authorization behavior, and prepare the application for the long-term vinext/Cloudflare Workers runtime.

**Architecture:** `src/shared/lib/auth.ts` becomes the stable Mkety Auth server boundary. Internal auth modules handle OIDC transactions, provider adapters, identity/session persistence, and authorization without exposing provider-specific types to application code. ZITADEL is implemented as an OIDC adapter; the application session is a Mkety-owned opaque cookie backed by hashed server-side session records.

**Tech Stack:** Next.js App Router, React 19, TypeScript 5.9, Drizzle ORM/PostgreSQL, `jose` 6.2.12 for standards-based JWT/JWK validation, Jest, Testing Library, vinext, Cloudflare Workers.

**Spec:** `docs/superpowers/specs/2026-09-06-mkety-auth-zitadel-cloudflare-design.md`

## Global Constraints

- Mkety Auth is the permanent application authentication boundary; ZITADEL is replaceable adapter infrastructure.
- `next-auth` and `@auth/drizzle-adapter` must be removed completely from application dependencies, lockfile, source, tests, and documentation.
- Authentication identity linkage must be provider-neutral; do not reuse Auth.js account semantics.
- The existing generic `accounts` table is retained for integration use until all callers are independently traced.
- Sessions are Mkety-owned opaque random tokens stored hashed server-side and delivered in HttpOnly/Secure/SameSite cookies.
- Protected tenant routes fail closed and continue using Mkety-owned roles/permissions.
- No production fake-login path may grant access.
- Cloudflare Workers is the target runtime; Containers are out of scope.
- `main` must not be changed, merged, or deployed until the feature branch is green and the user explicitly authorizes promotion.
- Cloudflare credentials are prepared by name only unless the user supplies/creates their secret values; never commit plaintext credentials.
